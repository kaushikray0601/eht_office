# idfviewer Baseline - 2026-06-18

## Purpose

`idfviewer` is currently an independent side app inside the EHT application. It is intended to become the foundation for model-assisted EHT design workflows, including route length extraction, model-based component placement, 3D review, and future integration with cold cable, BOQ, schedule, and SLD workflows.

## Current Scope

- Accept IDF, PCF, or IFC uploads, one source format at a time.
- Render normalized scenes in a static Three.js viewer.
- Save IDF/PCF preview scenes into lightweight database component rows.
- Keep IFC in preview mode until a dedicated large-model persistence strategy exists.
- Compare active IDF/PCF pipeline geometry against IFC reference geometry for nearest-structure analysis.

## Current Architecture

- `views.py`: upload, preview, save, library, saved-file rebuild, download, nearest-structure API.
- `parser.py`: custom IDF parser.
- `pcf_parser.py`: custom PCF parser.
- `ifc_parser.py`: IfcOpenShell preview parser.
- `services.py`: IDF/PCF scene persistence, conflict handling, saved-scene rebuild, download payload.
- `analysis_utils.py`: nearest-structure calculations.
- `static/idfviewer/js/viewer.js`: Three.js rendering and interactions.
- `models.py`: saved IDF/PCF files, components, save events, and future plot-plan overlay model.

## Known Boundaries

- IFC persistence is intentionally out of scope for the current save model.
- IDF/PCF persistence stores flexible component properties in JSON rather than a final query-optimized geometry schema.
- Plot-plan overlay is browser-only at the moment.
- Coordinate units are modeled at scene-normalization time for IDF, PCF, and IFC. PCF uses `UNITS-CO-ORDS` when declared; IDF currently assumes millimetres; IFC currently assumes metres until native IFC unit extraction is added.
- Project access scoping is not yet hardened for managed-project rules.
